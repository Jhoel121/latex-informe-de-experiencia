 """
 DADO: Un vehículo permaneció exactamente 1h 15min en el estacionamiento.
 CUANDO: El trabajador presiona "Dar Salida" en el panel.
 ENTONCES: Se liquida hora base + fracción proporcional exacta = S/ 6.25.
 """
 async def test_uat03_cobro_exacto_con_fraccion(self, db_session):
     fecha_ingreso = datetime(2026, 8, 20, 10, 0, 0, tzinfo=timezone.utc)
     fecha_salida = datetime(2026, 8, 20, 11, 15, 0, tzinfo=timezone.utc)
     charge = await calculate_charge(db_session, VehicleType.auto,
                                     fecha_ingreso, fecha_salida)

\subsection{2.3. OPTIMIZACIÓN DEL RENDIMIENTO}

Para asegurar que ParkSys mantenga tiempos de respuesta mínimos bajo condiciones de alta concurrencia en horas punta, se ejecutaron optimizaciones de ingeniería en dos capas: Frontend y Backend.




\subsubsection{2.3.1. Frontend: Lazy Loading y Standalone Components}

Angular 18 permite definir cada componente como Standalone (standalone: true), eliminando la necesidad de NgModules tradicionales. ParkSys aprovecha esta capacidad junto con Lazy Loading para reducir drásticamente el peso inicial de la aplicación. Los módulos de administrador, trabajador y conductor se cargan solo cuando el usuario navega a su sección correspondiente mediante \texttt{loadComponent()} en el archivo \texttt{app.routes.ts}.

\subsubsection{2.3.2. Backend y base de datos: asyncpg e indexación}

\textbf{Driver asíncrono asyncpg}

El uso del driver nativo asyncpg con SQLAlchemy 2.0 Async permite que FastAPI atienda múltiples peticiones concurrentes sin bloquear el hilo principal esperando respuestas de disco:

\begin{verbatim}
# backend/app/db/session.py
engine = create_async_engine(
 settings.database_url, # postgresql+asyncpg://...
 echo=settings.environment == "development",
 pool_pre_ping=True,
)

async_session_factory = async_sessionmaker(
 engine,
 class_=AsyncSession,
 expire_on_commit=False,
)
\end{verbatim}

\textbf{Resultado:} el servidor soporta más de 800 peticiones por segundo en benchmarks locales con uvicorn y el pool de conexiones de asyncpg.

\subsection{2.6. DESPLIEGUE DEL SISTEMA}

El despliegue de ParkSys se realizó bajo una arquitectura moderna y desacoplada, en la que cada capa del sistema se aloja en una plataforma especializada y todas se comunican entre sí de forma automática. El ecosistema productivo se apoya en cuatro herramientas principales: \textbf{Vercel} (interfaz visual), \textbf{Render} (lógica de negocio), \textbf{Supabase} (base de datos) y \textbf{GitHub} (control de versiones y orquestación CI/CD). Adicionalmente, el sistema integra proveedores externos para pagos, autenticación federada y correo electrónico.

Esta separación permite escalar, actualizar o reemplazar cada capa de manera independiente, sin afectar a las demás, y elimina la necesidad de configurar servidores o cableado de red manualmente.

\subsubsection{2.6.1. Frontend en Vercel (interfaz visual)}

\textbf{Responsabilidad.} Aloja exclusivamente el código de Angular 18 contenido en la carpeta \texttt{frontend/}.

\textbf{Funcionamiento.} Vercel actúa como una CDN (Red de Entrega de Contenidos) global que sirve la aplicación de página única (SPA) a los usuarios con baja latencia. Desde el navegador se ejecutan el renderizado de los mapas interactivos con Leaflet, los gráficos estadísticos con Chart.js y los estilos construidos con Tailwind CSS y Angular Material. Gracias a la configuración de \textit{Hash Routing}, Vercel puede atender redirecciones directas provenientes de pasarelas de pago (por ejemplo, el retorno desde Stripe Checkout) sin perder la ruta de la aplicación.

\textbf{Automatización.} Vercel detecta cualquier \texttt{git push} sobre la rama \texttt{main} de GitHub, ejecuta la compilación estricta de Angular (\texttt{npm run build}) y reemplaza la versión en vivo (\texttt{park-sys-delta.vercel.app}) por la nueva, sin caídas de servicio.

\subsubsection{2.6.2. Backend en Render (lógica de negocio)}

\textbf{Responsabilidad.} Aloja y ejecuta el servidor API asíncrono construido en Python con FastAPI (carpeta \texttt{backend/}).

\textbf{Funcionamiento.} Render es el "cerebro" del sistema en la nube. Recibe las peticiones del frontend (inicio de sesión, creación de reservas, registro de ingresos y salidas), procesa las reglas de negocio (como el cálculo de cobros al minuto según la tolerancia configurada y la generación de comprobantes PDF con ReportLab) y gestiona la seguridad mediante tokens JWT. Además, mantiene activas las conexiones WebSocket en tiempo real, de modo que la pantalla de la garita se actualiza automáticamente cuando se registra un cobro o una reserva.

\textbf{Automatización.} Render escucha a GitHub a través del flujo CI/CD. Cuando hay cambios en el código Python, o nuevas librerías en \texttt{requirements.txt}, construye un nuevo contenedor a partir del \texttt{Dockerfile}, instala las dependencias desde cero y ejecuta las migraciones de base de datos (\texttt{alembic upgrade head}). Solo cuando el nuevo servicio arranca correctamente, apaga el anterior, lo que evita tiempos de inactividad en la API (\texttt{parksys-59uv.onrender.com}).

\subsubsection{2.6.3. Base de datos en Supabase}

\textbf{Responsabilidad.} Provee el servidor en la nube para la base de datos relacional PostgreSQL del sistema.

\textbf{Funcionamiento.} Supabase es el almacenamiento definitivo y persistente de ParkSys. Conserva las cuentas de usuario, los perfiles y vehículos registrados de los conductores, el estado en tiempo real de los cajones de estacionamiento, las transacciones de Stripe y el historial de auditoría. El backend alojado en Render se conecta a Supabase mediante el motor \texttt{asyncpg} y SQLAlchemy 2.0 asíncrono, realizando consultas y escrituras de forma continua y concurrente.

\subsubsection{2.6.4. GitHub: control de versiones y orquestación CI/CD}

\textbf{Responsabilidad.} El repositorio \texttt{Jhoel121/ParkSys} es la bóveda central que resguarda todo el código fuente y su historial de cambios.

\textbf{Funcionamiento.} GitHub actúa como interruptor principal y director de orquesta. Cuando el desarrollador sube cambios con \texttt{git push}, GitHub recibe el código y dispara \textit{webhooks} de forma simultánea hacia Vercel y Render, comunicándoles que existe código nuevo validado en la rama principal. Ambas plataformas inician entonces su proceso de actualización, y el despliegue completo a producción es limpio, predecible y no requiere intervención manual sobre servidores.
